# Сверка ТЗ рефакторинга CRM: требования вне тестов

Дата актуализации: 2026-11-26. Основа: `ТЗ рефакторинг CRM.docx`, текущий `master` после подэтапов 8.x.
Тестовые требования и coverage в этой сверке не оцениваются; сведения о проведённых проверках указаны только как подтверждение сохранения поведения.

## Итог

Целевые backend-границы и внедрение Prisma через `createApp(deps)` реализованы; frontend использует React Router, TanStack Query, URL-состояние основных разделов, Auth Context и общие состояния загрузки/ошибки. Вне тестов основное рефакторинговое ядро завершено. В последних подэтапах разделены request service, состояние страниц досок и базы знаний, а выбор Telegram-организаций/точек вынесен в отдельный resolver. API-контракты и схема БД сохранены.

Полное буквальное совпадение со всеми структурными пунктами ТЗ не достигнуто. Оставшиеся отклонения ниже перечислены отдельно; они не скрыты за прежними сведениями о крупных файлах, которые уже были разделены.

## Оставшиеся отклонения и причины

| Требование ТЗ                                                           | Текущий статус                                                                                                                                                                                                                                            | Причина или ограничение                                                                                                                                                                                                                                                                                                 |
| ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Docker-сценарий, установка Windows-служб и production/LAN-развёртывание | Не выполнялись. Локальная CRM запускается вручную без служб.                                                                                                                                                                                              | Пользователь прямо указал, что Docker не нужен и запускать следует без служб. Это зафиксировано в [отчёте этапа 7](stage-7-cleanup-docs-deployment.md) и [отчёте этапа 8](stage-8-report.md).                                                                                                                           |
| Перенос request-валидации из сервисов в middleware                      | Zod-схемы остаются в операциях сервиса.                                                                                                                                                                                                                   | Перестановка проверки относительно авторизации и проверки существования записи может менять статус/тело ответа. Сохранение API-поведения — часть текущего задания; исключение описано в [отчёте 8.4](stage-8-4-requests-report.md).                                                                                     |
| Компонент с буквальным именем `RequireRole`                             | Отдельного компонента нет; проверка доступности маршрутов и отказ в доступе реализованы текущей системой permissions и `AccessDeniedPage`.                                                                                                                | Сохранено поведение контроля доступа без повторения отсутствовавшего в исходной архитектуре компонента; причина и выбор описаны в [отчёте 8.5](stage-8-5-frontend-report.md).                                                                                                                                           |
| Точная физическая структура frontend-папок из схемы ТЗ                  | Функциональные границы и lazy-маршрутизация есть, но не каждая фича разложена буквально на `api.ts`, `pages/` и `components/`.                                                                                                                            | Уже существующая структура организована по фичам; полное массовое перемещение файлов не улучшает контракты и повышает риск шума/ошибок при сохранении поведения. Сведения о границах приведены в [инвентаризации](inventory.md).                                                                                        |
| Ориентир размера отдельных файлов и factory-hook функций                | Request-операции и страницы разделены по ответственности, но фабрики/хуки сохраняют замыкания над общими состояниями и зависимостями; `bot-handlers.ts` также содержит диспетчеризацию Telegram-событий. В проекте остаются другие файлы более 200 строк. | Это не функциональный пробел. Дальнейшее дробление требует переносить связанные состояния и зависимости между границами модулей; ориентир размера не трактуется как требование менять поведение или создавать искусственные слои. Крупные текущие файлы и возможные границы приведены в [инвентаризации](inventory.md). |

## Проверки сохранения поведения

В ходе этих подэтапов полный `npm.cmd run verify` завершился успешно: frontend и backend TypeScript, ESLint, Prettier, frontend 10/10 и backend 116/116 прошли; миграций к применению и schema diff нет; production-сборки, SPA smoke и Playwright 12/12 прошли. Characterization и E2E использованы как регрессионное подтверждение, но не как критерии этой сверки.

Кириллические тексты в изменённых исходниках сохранены в UTF-8; проверка кодировки проекта прошла.

## Границы

Сверка охватывает архитектуру, код, документацию и локальный запуск вне тестовых требований. Docker и Windows-службы исключены из работы по прямому указанию пользователя. Схема БД, маршруты, форматы ответов и порядок наблюдаемых проверок API сохраняются.
