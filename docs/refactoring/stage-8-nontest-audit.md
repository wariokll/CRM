# Сверка ТЗ рефакторинга CRM: требования вне тестов

Дата актуализации: 2026-11-27. Основа: `ТЗ рефакторинг CRM.docx`, рабочая ветка `master`. Проверка сфокусирована на коде, архитектуре, API/БД, документации и локальном запуске; тесты учитываются только как регрессионное подтверждение.

## Итог

Основные функциональные этапы рефакторинга завершены. Backend использует модульные routes/controllers/services и фабрику `createApp(deps)`; frontend использует React Router, TanStack Query, URL state и feature hooks. Крупнейшие области, отмеченные в предыдущей сверке, дополнительно разделены по ответственности. Внешние API контракты, порядок наблюдаемых HTTP ответов и Prisma schema сохранены.

Полное буквальное совпадение со всеми структурными примерами ТЗ не достигнуто. Оставшиеся отклонения указаны ниже отдельно. Развертывание через Docker, Windows services и production/LAN намеренно исключены по прямому указанию пользователя.

## Оставшиеся отклонения и ограничения

| Требование ТЗ                                                                                   | Статус                                 | Причина / решение                                                                                                                                                                                                                                                                                           |
| ----------------------------------------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Docker, установка Windows services, production/LAN deployment                                   | Исключено                              | Пользователь прямо указал, что Docker не нужен и запускать следует без служб. Эти варианты развертывания не входят в согласованный объём. Приложение запускается локально вручную.                                                                                                                          |
| Перенос request body validation из сервисов в middleware                                        | Выполнено                              | Create body разбирается после `authenticate` и перед чтением access. Для update middleware сначала получает access и видимую заявку через service preparation, затем запускает Zod body validation. Существовавший порядок проверок и формат ошибок сохранены; policy и бизнес-проверки остаются в сервисе. |
| Guards `RequireAuth` / `RequireRole`                                                            | Выполнено                              | Оба компонента подключены к app shell. `RequireRole` использует прежний `buildNavigation` как единственный источник прав; `RequireAuth` показывает те же boot, login и inactive-account экраны.                                                                                                             |
| Не более четырёх позиционных параметров функции                                                 | Выполнено                              | Все прежние функции с пятью параметрами переведены на именованные объектные аргументы. Текущий AST-аудит исходников не находит функций с более чем четырьмя позиционными параметрами.                                                                                                                       |
| Физическая структура frontend features                                                          | Выполнено                              | TSX файлы разложены по `components/`, `pages/` и `hooks/`; feature-specific типы размещаются в `types/`, если они есть. API/query модули остаются в feature root, чтобы страницы и hooks могли импортировать их без лишнего barrel слоя. Root `api.ts` и `types.ts` являются только реэкспортами.           |
| Ориентир размера файлов около 300 строк, функций около 50 строк, UI-компонентов около 200 строк | Выполнено с обоснованными исключениями | Исходники не превышают 298 строк; UI-компоненты не превышают ориентир 200 строк. Остаточные длинные функции перечислены и обоснованы ниже по их составной роли; границы уже выделены в отдельные сервисы, hooks и компоненты.                                                                               |

### Обоснованные исключения по размеру функций

ТЗ допускает отступления от ориентиров при документированном обосновании. Следующие hooks координируют URL, кеш запросов, React state и обработчики: `useKnowledgeSelection` (199 строк), `useBoardsPage` (182), `useBoardActions` (166), `useKnowledgeEditor` (156), `useOrganizationActions` (98), `useKnowledgeImport` (91), `useAppData` (85), `useKnowledgeArticleSave` (72), `useKnowledgeAttachments` (71). Их отдельные операции уже вынесены в соседние hooks/components; оставшийся код hook связывает общее состояние и порядок побочных эффектов.

Обоснованные backend исключения: `buildRequestReport` (151 строка) и `buildProcurementReport` (67) собирают несколько метрик из одного авторизованного набора Prisma данных; `createBoardDragHandler` (118) координирует оптимистичный DnD и восстановление после конфликтов; `main` Telegram-бота (62) распределяет типы событий в рамках общей сессии; `generateRecurringOccurrence` (58) и `resolveRequestTarget` (53) сохраняют порядок проверки и записи связанных сущностей; `restoreArchivedCard` (55) транзакционно восстанавливает архивную карточку; `sendToChat` (51) обрабатывает отправку Telegram-сообщения, повторы и ошибки. Дальнейшее дробление этих тел либо дублирует общие запросы и состояние, либо разносит последовательность по обёрткам. Их входы, выходы и обязанности явны.

Фабрики `create*Service` и `create*Controllers` также длиннее 50 строк, потому что связывают зависимости (включая Prisma client) с именованными операциями и возвращают API модуля. Эти фабрики служат composition roots уровня модуля. Повторно передавать одинаковые зависимости в каждую операцию или создавать DI-контейнер здесь не требуется. Строки файлов и актуальные верхние значения приведены в `inventory.md`.

## Проверка после завершающих изменений

Последний полный `npm.cmd run verify` завершился успешно: проверка UTF-8; frontend/backend TypeScript; ESLint; Prettier; frontend 10/10; backend 116/116; production builds; SPA fallback smoke; Playwright 12/12. Prisma сообщила об отсутствии pending migrations и schema diff. Изменения в API и БД не вносились.

## Границы сверки

Не включены пункты, требующие Docker, установки служб или production/LAN окружения. Не менялись DB schema, миграции, endpoint payloads и порядок проверок, от которого зависят HTTP ответы.
